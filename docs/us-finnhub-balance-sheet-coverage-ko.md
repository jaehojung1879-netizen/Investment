2026-10-07부터 수집된 Finnhub 공시 618건에 재무상태표(balance sheet)가 없다.

## 0. 결론: 다섯 가지 질문에 대한 답

**1. 왜 최근 공시 618건에 재무상태표가 없는가?**
**아직 확정할 수 없다. 저장된 증거로 확정되는 것은 원인이 어디에 있는지까지다.**

- 현상은 *수집기가 응답을 받은 시점*에 이미 생겼다. 저장된 `bs` 목록 자체가 비어 있고, 어떤 특징 계산 코드도 거기에 도달하지 못했다.
- 그 원인은 두 가지 중 하나다.
  - (A) 공급자가 `report.bs`를 비워서 보냈다.
  - (B) 공급자가 재무상태표를 수집기가 읽지 않는 키로 옮겼다.
- 수집기는 `report.get("bs")`만 저장하고 원본 응답과 키 구조를 남기지 않는다. 그래서 두 가설은 저장본만으로 구별되지 않는다.
- 이 사실이 이번에 확인된 *수집기 쪽 결함*이다. 원인이 아니라 증거를 지우는 구조의 결함이다.
- 공급자 변경 여부는 가정하지 않았다. 다만 "공급자가 새로 서빙하기 시작한 공시에서만 생겼다"는 패턴은 확인했다(아래 2번 표).

**2. 기존 소스 증거로 누락된 값을 복구할 수 있는가?**
**없다. 복구 0건이다.**

- 총자산은 재무상태표에만 있다. 같은 공시의 손익계산서·현금흐름표에는 없고, 저장소 안의 다른 PIT 소스도 이 값을 갖고 있지 않다.
- 이전 분기 공시의 총자산을 빌려 쓰는 것은 기간이 다른 값을 다른 기간의 값으로 바꿔 부르는 것이다. 다른 회사나 이후 공시에서 가져오는 것도 마찬가지이므로 금지한다.
- 따라서 실제 데이터의 "수정 후" 커버리지는 "수정 전"과 같다. 아래 4번 표에 그대로 적었다.

**3. 전향 현금 수익성 신호는 지금 측정 가능한가?**
**아니다.** 저장본 기준으로 2026-10-09에 S&P 500 503개 종목 중 4개(0.80%)만 계산된다.

- 재무상태표 누락은 이유의 절반이다. 나머지 절반은 *공시 시차*다.
- 저장본에는 2026-09-15부터 10-06 사이에 수집된 레코드가 한 건도 없다. 레코드의 수집일(`collectedAt`)은 9/13, 9/14, 10/7~11뿐이다. 이 기간에 야간 수집은 돌았지만(커밋 10/2~10/6) 공급자가 새 공시를 주지 않았다.
- 그 사이 Q1 공시가 180일 stale 규칙(9/27)에 걸려 10월 2일에 이미 449개 종목이 `REPORT_STALE_OVER_180_DAYS`가 된다.
- 10/8에 들어온 Q2 공시는 총자산이 없어 460개 종목이 `ASSETS_NOT_STATED`다.

**4. 무엇이 여전히 막혀 있는가?**

- 원인 A/B의 구별: 소유자의 프로브 1회(최대 12콜) 또는 개선된 수집기의 다음 야간 실행.
- 총자산의 실제 복구: 프로브 결과에 따라 달라진다. 공급자가 서빙하지 않으면 `BLOCKED_SOURCE`다.
- 전향 신호의 정의: 동결되어 있다(`us_cash_profitability.py` 해시 불변). 보완 소스를 쓰려면 새 특징 계약 버전이 필요하다(프로토콜 P5).

**5. 소유자가 다음에 정확히 할 일**

1. 이 PR을 검토한다. 병합은 소유자의 결정이다. 병합하면 *다음 야간 수집부터* 수집기가 건전성 관찰을 `response-health.json`에 기록한다(아래 6번 참고).
2. (권장, 약 1분) 본인 키로 프로브를 한 번 실행한다. 명령은 복구 계획 `S0_PROBE`에 있고, 결과 `probe.json`과 원본 응답 `probe-raw.jsonl.gz`를 알려 주면 된다. 이것이 A/B를 가르는 가장 빠른 측정이다.
3. 프로브 결과에 따라 복구 계획의 S2(보완 수집, 최대 700콜) 또는 S3(공급자 문의, `BLOCKED_SOURCE`) 중 하나를 승인한다. 둘 다 이 변경에 포함되어 있지 않다.

## 1. 무엇을 읽었는가

- **읽은 코드:** 수집 스크립트 `collect_finnhub_fundamentals.py`, `finnhub_fundamentals.py`, `finnhub_derive.py`, `us_cash_profitability.py`, `fundamentals.yml`, PR #232의 사전점검 보고서와 JSON.
- **읽은 증거:** signal-history 브랜치의 `ledger/fundamentals/us` 불변 샤드 17개를 *읽기만* 했다. 감사는 얕은 clone에서 `git archive 4ddeb87`로 꺼낸 사본을 읽는다. 커밋 `4ddeb87bac078f2681fa83b1225111896edb319b`(2026-10-11)는 그 시점의 마지막 US 슬라이스이며, 감사 JSON에 샤드별 SHA-256이 들어 있다. 같은 커밋이면 JSON이 바이트 단위로 재현된다(테스트).
- **하지 않은 것:** 공급자 호출. 이 환경에는 `FINNHUB_API_KEY`가 없고 `finnhub.io`로 가는 경로도 없다. 키를 노출하거나 우회하거나 대량 재수집을 한 일은 없다.
- **증거 공백(정확히):**
  - 원본 응답 바이트가 저장되어 있지 않다.
  - 응답의 키 구조가 저장되어 있지 않다.
  - 이미 저장된 공시를 다시 서빙받은 사본은 비교 없이 버려졌기 때문에 공급자가 나중에 재무상태표를 채웠는지 알 수 없다.

## 3. 원인 판정 (확인과 가설의 구별)

| 후보 | 판정 | 근거 |
|---|---|---|
| A. 공급자가 재무상태표를 아예 보내지 않았다 | **미결 (반박되지 않음, 확정되지 않음)** | 저장된 값이 빈 목록이다. 공급자가 `[]`을 보냈는지는 원본이 없어 알 수 없다. |
| B. 응답 스키마나 계정명이 바뀌었다 | **미결** | 재무상태표가 다른 키로 와도 수집기는 `[]`로 저장한다. A와 구별되지 않는다. 손익계산서·현금흐름표의 어휘는 *바뀌지 않았다*(아래). |
| C. 연간/분기 요청 동작이 바뀌었다 | **반박됨** | 분기 574건과 연간 45건 모두 100% 누락이다. 한 빈도만의 문제가 아니다. |
| D. 수집기가 응답을 자르거나 잘못 정규화했다 | **응답 전체의 절단은 반박됨** | 10월 코호트의 손익계산서 항목 수 중앙값이 참고 표본의 1.000배, 현금흐름표 1.031배다. 참고 표본에 있던 계정(20건 이상)이 10월에 빠진 것도 없다. 다만 "특정 키 하나만 못 읽는" 경우는 B와 같다. |
| E. 중복 제거가 유효한 레코드를 가렸다 | **저장된 공백의 원인으로는 반박됨** | 10월 레코드 619건 중 이전 저장본과 id가 겹치는 것은 0건이다. 처음 보는 공시가 처음부터 비어 있었다. |
| E2. 중복 제거가 *이후의 보완본*을 가리고 있을 수 있다 | **저장본으로는 검증 불가** | 이미 저장된 id는 매 실행에서 비교 없이 건너뛴다(first write wins). 공급자가 나중에 채워도 저장본은 알 수 없다. 이것이 수정으로 고친 결함이다. |
| F. PIT 가시성이나 계정 분류가 유효한 재무상태표를 없는 것으로 표시했다 | **원인으로는 반박됨** | 저장된 `bs` 목록이 특징 코드 이전에 이미 비어 있다. 가시일 규칙(`max(availableFrom, acceptedDate)` 다음 날)은 바뀌지 않았다. |

확인된 것(저장본에서 직접 읽은 사실):

- 10월 코호트의 재무상태표는 100% 비어 있고, 9월은 0.414%였다.
- 누락은 새로 서빙된 공시에서만 나타난다.
- 손익계산서와 현금흐름표는 정상이다.
- 수집기가 원본 응답을 남기지 않는다.

가설(증거가 가리키지만 확정이 아닌 것):

- 공급자의 갱신이 2026-06-26부터 10-07까지 멈췄다가 변경된 형식으로 재개됐다.

## 5. 수정 내용: 증거를 남기는 최소 변경 (값을 만들지 않음)

원인이 확정되지 않았으므로 파서나 값은 고치지 않았다. 고친 것은 *증거를 지우는 구조*다.

1. **`pipeline/finnhub_response_health.py`** (신규, 순수 관찰)
   - 서빙된 각 공시의 재무상태표 상태를 5가지로 구분한다: 총자산 있음, 재무상태표만 있고 총자산 없음, `bs`가 빈 목록, `bs` 키 없음, 섹션 전무.
   - 응답과 `report`의 키 집합을 세고, 수집기가 모르는 키를 따로 표시한다. 재무상태표가 이름만 바뀐 경우(B)를 놓치지 않기 위해서다.
   - 이미 저장된 공시가 다시 서빙되면 저장본과 비교한다: 저장본에는 없고 이번에는 있음(보완 후보, E2), 저장본에는 있고 이번에는 없음(공급자가 *덜* 주는 중), 섹션 내용이 바뀜.
   - 새 공시의 5%를 넘게 총자산이 없으면 `degraded`로 표시한다. 정상 수준의 약 12배이며, 5%는 정상값(0.4%)보다 한 자릿수 위의 경고선이다.
   - `balance_sheet_quarantine`은 읽기 전용 격리 뷰다. 레코드를 고치지 않는다.
2. **`scripts/collect_finnhub_fundamentals.py`** (관찰만 추가)
   - 각 응답 공시를 건전성 객체에 넘기고, 실행 요약을 출력하고, 같은 폴더의 `response-health.json`에 최근 60회 이력을 기록한다.
   - 이 파일은 `finnhub-*.jsonl.gz` 글롭에 걸리지 않고, 기존 `windows.json`·`inventory.json`처럼 매 실행에서 다시 쓰는 부속 파일이다.
   - `degraded`면 GitHub 경고 주석(`::warning`)을 출력하되 **종료 코드는 바꾸지 않았다.** 손익·현금흐름 데이터의 야간 커밋을 막지 않기 위해서다.
   - 같은 실행에서 연간과 분기 요청이 같은 공시를 주면 두 번째 사본은 재서빙으로 센다.
3. **`scripts/probe_finnhub_balance_sheet.py`** (소유자 실행용, 호출 상한 20)
   - 분기 요청 `from=2026-01-01` 한 번의 응답에 Q1(9월에 재무상태표 있음)과 Q2(10월에 없음)가 함께 들어온다. 같은 응답이 스스로 대조군이다.
   - 판정 4종과 불확정 1종: 새로 서빙된 공시에서만 누락 / 엔드포인트 전체에서 누락 / 공급자가 나중에 채움 / 다른 키에서 발견 / 불확정.
   - 응답 원본을 gzip으로 보존한다(수집기가 남기지 않았던 증거). API 키는 출력·저장하지 않고 오류 문구에서 지운다.

바꾸지 않은 것(테스트로 고정):

- 저장된 샤드 바이트. 재서빙이 더 풍부하든, 더 빈약하든, 내용이 바뀌었든 같다.
- `build_record`, `finnhub_fundamentals.py`, `finnhub_derive.py`, `us_cash_profitability.py`. 해시가 P4 사전점검이 고정한 값과 일치한다.
- PIT 가시일 규칙, TTM 롤포워드, 총자산의 기간·통화 의미.
- 워크플로 전부(`fundamentals.yml`, `tests.yml`, `probes.yml`), `docs/results/*`, 가격 수집기와 그 저장 경로, #231이 건드리는 파일.

**병합의 효과:** 수집기 스크립트는 야간 워크플로가 매번 `main`에서 실행하므로, 병합하면 *다음 야간 수집*부터 건전성 이력이 기록된다. 저장되는 공시 레코드는 달라지지 않는다. 이 변경은 어떤 수집도 실행하지 않았다.

## 6. 보존한 불변식과 검증

- **append-only:** 수집기를 합성 공급자로 3번 돌린다. 저장본에 재무상태표가 없던 공시를 이후 완전한 사본이 서빙해도, 또 빈 사본이 서빙해도 샤드 바이트가 같고, 보완 후보만 보고된다.
- **September 동일 파싱:** 9월 형식 공시는 변경 전과 같은 레코드가 된다. 10월 형식은 `bs == []`이고 그 외 모든 것이 같다. 영(0)이나 빌려 온 값이 없다.
- **총자산 부재는 이유 코드:** 현재 공시에 총자산이 없으면 비율은 `None`과 `ASSETS_NOT_STATED`다. 직전 공시의 총자산(1000)이나 0으로 바뀌지 않는다.
- **TTM·가시일 불변:** 재무상태표 유무와 상관없이 TTM 영업현금흐름(150−60+80)과 가시일이 같다.
- **감사의 결정성:** 같은 저장소면 감사 JSON이 바이트 단위로 같고, 감사는 수익률·IC·포트폴리오를 계산하지 않으며 봉인 결과 경로에 쓰기를 거부한다.
- **보호 경로:** 위 목록의 워크플로·파일이 이 변경에서 수정되지 않았음을 `git diff` 기반 테스트가 검사한다.
- 로컬에서 실행한 점검: `ruff check .`, `compileall`, 새 테스트 24개와 관련 기존 테스트(합계 163 passed). 전체 테스트 스위트와 seed 생성·산출물 검증 결과, 그리고 CI 최종 상태는 PR 본문과 마지막 보고에 적는다.

## 7. 이 문서가 하지 않는 주장

- 공급자가 API를 바꿨다고 말하지 않는다. 공급자가 재무상태표를 의도적으로 뺐다고도 말하지 않는다.
- P4(과거 탐색 실행)는 영향을 받지 않는다. 마지막 성숙 신호일 2026-06-05 이전에 보이는 재무상태표 없는 공시는 6건(5개 종목)뿐이고, 그 신호일에는 동결된 규칙대로 이전 공시로 돌아가거나 표본에서 빠진다. 이 사실은 #232에서 이미 공개되어 있다.
- 이 PR은 어떤 백필도, 프로덕션 수집도, 워크플로 실행도 하지 않았다.
