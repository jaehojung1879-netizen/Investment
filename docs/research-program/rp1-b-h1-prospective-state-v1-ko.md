# rp1-b-h1-state-v1 — Track B B-H1 전향 시장 상태 영수증 (사전등록)

- **상태:** `PREREGISTERED_PROSPECTIVE_STATE_RECORD`. 상태 관측만 등록한다. H63 성과 평가는 `BLOCKED_OUTCOME_CONTRACT_NOT_REGISTERED`.
- **고정 명세:** `docs/research-program/specs/rp1-b-h1-state-v1.json`
- **구현:** `pipeline/rp1_b_h1_state.py`, `scripts/record_rp1_b_h1_state.py`. 호출 지점은 `scripts/update_ledger.py`의 마지막 hook이다.
- **기록 위치:** signal-history `ledger/research-strategies/rp1-b-h1-state-v1/`
  - `receipts.jsonl`: 증거
  - `attempts.jsonl`: 보류·거부 시도 기록. 증거가 아니다.
  - `coverage.json`: 기록 현황
  - `publication-status*.json`: 단계별 상태
- **효과:** `productionEffect: NONE`. 주간 판단, 주문, 비중, Track A·C의 어떤 원장에도 들어가지 않는다.

## 1. 무엇을 기록하는가

매주 KR 주간 판단 세션 종가를 기준으로, 다음 세션 개장 전에 아래 값을 영수증 한 줄로 고정한다.

| 항목 | 정의 | 출처 |
|---|---|---|
| FAST | 봉인 `kr_market_risk_model.fast_states`. 종가 < 200일 평균, 연율 변동성63 > 25%. 신호 세션까지의 KRX 201세션을 쓴다 | `03-studies-abc-ko.md` B.2, kr-market-risk-model-v1 |
| 24개월 수익 | 신호 세션 종가 / 기준 세션 종가 − 1. 기준 세션은 신호일 − 24개월 이하의 마지막 KRX 세션이다. 그 세션 자체가 유효해야 하며 허용 오차는 없다 | B.3, #264 preview |
| B-H1 불리 | FAST == 2 **또는** 24개월 수익 < 0 | B.3 |
| 결측 규칙 | 판정된 다리 하나가 불리하면 True. 그렇지 않고 한 다리가 미판정이면 None. 두 다리가 모두 판정되고 둘 다 양호할 때만 False | #264 |

- **원 정의는 바꾸지 않았다.** 창, 임계값, 지연, 지평 모두 원 정의 그대로다.
- **추가한 것은 무결성 규칙뿐이다.** 이 규칙은 다리를 제거할 수만 있고, 다리를 만들 수는 없다.
- **#264 preview의 계산을 그대로 호출한다.** 다만 입력 시계열을 먼저 KRX 달력에 맞춘다.

### 원천

`FDR_KS200`(KOSPI 200 가격지수, `finance-datareader==0.9.110`)를 쓴다. 봉인된 FAST의 입력과 같은 원천이고, README B 진단도 이 원천을 썼다.

- **경로:** FDR는 `KS200`을 FinanceData의 공개 연도별 CSV 캐시(`fdr_krx_data_cache`)에서 읽는다.
- **연도 파일 실패가 조용히 묻힌다.** 한 해 파일을 받지 못해도 오류 없이 그 해를 건너뛴다. 그래서 달력에 맞춘 뒤에 남은 구멍을 결측으로 처리한다.
- **대체 원천은 없다.** 다른 vendor나 다른 지수로 바꾸지 않는다.
- **원 행은 저장하지 않는다.** 영수증에는 파생값과 아래 정보만 남긴다.
  - 제공 범위와 행 수
  - 제공 행의 SHA-256
  - 달력 정렬 창의 SHA-256

**실데이터 가용성 점검 (2026-10-24 02:01 UTC, 결과 없음).** 상태값은 출력하지 않았다.

- 2026-10-23(금) 세션은 토요일 오전에 이미 제공되었다.
- 2024-09-13~2026-10-23의 509세션이 모두 `VALID`였다. 달력에 없는 날짜 행은 0개였다.
- 두 다리 모두 판정 가능했다.

## 2. 기록 규칙

| 규칙 | 구현 |
|---|---|
| 세션 선택 | 기록자 시계로 정한다. 실행 시점에 종가가 확정(18:00 KST)된 마지막 KRX 세션이다. site artifact를 읽지 않으므로 생산 빌드 내용과 독립적이다 |
| 기록 창 | 신호 세션 18:00 KST 이후, 다음 세션 09:00 KST 전 |
| 쓰는 순간의 시각 | 다운로드 뒤 `createdAtUtc`를 다시 찍고, 바이트를 쓰기 직전에 한 번 더 확인한다(Track A `append_live_receipt` 재사용). 09:00 정각은 창 밖이다. 다운로드나 쓰기 도중 창이 닫히면 `REFUSED` |
| 달력 정렬 | `kr_bar_integrity.calendar_frame`을 쓴다 |
| 미래 데이터 | 신호 세션 뒤 날짜의 행이 하나라도 있으면 `REFUSED`. 조용히 버리지 않는다 |
| 중복 | 같은 `(studyId, signalDate)`는 다시 쓰지 않는다(`SKIPPED`). 다운로드 전에 확인한다. vendor 중복 날짜는 `REFUSED` |
| 원장 | append-only JSONL이다. 행마다 SHA-256 digest와 `previousReceiptSha256` 체인을 둔다. 읽을 때마다 아래 항목을 모든 행에서 다시 도출하고 검증한다. 하나라도 어긋나면 원장 전체를 거부하고 이후 추가도 거부한다 |
| 꼬리 고정 | 체인은 마지막 행이 잘린 것을 스스로 알 수 없다. 그래서 LIVE 영수증마다 `ledgerAnchor`(추가 당시 signal-history HEAD, 그 커밋이 담은 영수증 수, 마지막 digest)를 둔다. 추가 전과, 영수증이 0개인 경우를 포함한 모든 등록 coverage 실행마다 두 가지를 확인한다. 실패하면 coverage는 정상 보고 대신 `LEDGER_INTEGRITY_FAILED`만 낸다. git 이력의 모든 `receipts.jsonl` 판이 다음 판과 작업 파일의 바이트 접두사여야 하고(커밋된 절단 `LEDGER_HISTORY_NOT_APPEND_ONLY`, 커밋 전 절단 `LEDGER_TAIL_REWRITTEN`), 모든 영수증의 anchor 커밋이 HEAD의 조상이면서 주장한 행을 정확히 담아야 한다(`LEDGER_ANCHOR_COMMIT_NOT_IN_HISTORY`). git 밖의 원장에는 LIVE 영수증을 쓸 수 없다 |
| 공급자 장애 | 아래 표 |
| 독립성 | Track A·C·봉인 연구의 영수증과 별도 원장이다. 공유하는 것은 `prospective_receipt_core`뿐이다 |

**달력 정렬에서 처리하는 것**

| 경우 | 처리 |
|---|---|
| 행 없음 | `SESSION_MISSING` |
| 거래량 결측·비유한·음수 | `VOLUME_INVALID` |
| 거래량 0 | `SUSPENDED` |
| 종가 무효 | `CLOSE_INVALID` |

이 네 경우의 세션에는 종가가 없다. 창은 행 수로 세지 않는다. 그래서 세션이 하나 빠지면 그 창은 짧아지는 것이 아니라 구멍이 난다. Track A의 `VOLUME_INVALID` 수정을 그대로 유지한다.

**원장을 읽을 때 행마다 다시 도출하는 것**

- 행의 digest
- 다리 값
- 불리 판정
- 기준 세션
- 체결 세션
- 기록 창

**탐지 한계:** 마지막 영수증과 그것을 담은 모든 커밋을 force push로 지우는 이력 재작성은 저장소 혼자서는 알아낼 수 없다. 그 뒤에 그 영수증을 anchor로 삼은 영수증이 아직 없는 경우다. 이때 독립 기록은 기록 실행의 Actions job log(`receiptSha256` 출력)뿐이다. 새 저장소·App·외부 저장소는 도입하지 않았다. ledger workflow의 `git fetch origin signal-history`는 depth 1 checkout에서도 브랜치 이력 전체를 가져온다(2026-10-24 측정: 693커밋, main 커밋만 shallow).

**공급자 장애 처리**

| 경우 | 처리 |
|---|---|
| 다운로드 실패, 빈 응답, 신호 세션 종가 미제공 | `DEFERRED`. 창이 닫히면 그 주는 `MISSED`이며 사후에 채우지 않는다. `coverage.json`은 영수증이 0개여도 매 실행 쓴다(등록 시각은 첫 영수증, 없으면 git main에서 읽는다). 첫 주가 누락되어도 창이 닫히는 즉시 마지막 시도 사유(없으면 `NO_ATTEMPT_RECORDED`)와 함께 보고된다 |
| 창 안 구멍 또는 달력 외 행 | 다음 개장까지 24시간 넘게 남았으면 `DEFERRED`. 24시간 이내면 해당 다리를 미판정 사유와 함께 기록한다 |

### 실행 경로

`ledger.yml` → `update_ledger.py` 순서로 실행된다. Track A의 두 기록기 뒤에 `run_isolated`가 자식 프로세스로 돈다.

- **제한 시간:** 600초. vendor 읽기에는 socket 30초 제한이 따로 있다.
- **격리:** 거부, 예외, 크래시, 시간 초과는 이 연구의 `publication-status.json`에 `failedSteps`로 남는다. workflow 경고도 남긴다. paper ledger, Track A, commit 단계는 영향을 받지 않는다.
- **식별:** 메인 Actions가 성공하고 B만 실패한 경우는 두 곳에서 알 수 있다.
  - job log의 `::warning::rp1-b-h1-state-v1 ...`
  - signal-history의 `publication-status.json`의 `status: STEP_FAILED`
- **workflow는 바꾸지 않았다.** `.github/workflows`는 트리 hash로 고정되어 있다.

**예상 주기**

- 00:10 UTC cron은 실제로 04:30 UTC 전후에 시작한다.
- 토요일 실행은 금요일 세션을 기록한다. 공급자 구멍이 있으면 보류한다. 이때 다음 개장까지 약 43.5시간이 남아 있다.
- 일요일 실행은 최종 시도다. 다음 개장까지 약 19.5시간이 남아 있다.
- 평일 실행은 창 밖이라 건너뛴다.

**한계:** 빌드나 검증 단계가 실패한 날에는 `update_ledger.py` 자체가 돌지 않는다. 그런 날은 어느 연구도 기록하지 못한다. 이 PR은 workflow를 바꿀 수 없으므로 이 한계를 그대로 둔다.

## 3. 사전등록과 첫 기록 조건

1. **승인.** 이 PR이 병합되는 것이 상태 기록의 승인이다. 병합 시각은 `origin/main`의 first-parent 이력에서 명세를 추가한 커밋으로 읽는다(Track A의 `registration_from_git` 재사용).
   - 병합되지 않은 브랜치는 거부한다.
   - 그 커밋을 포함하지 않는 코드도 거부한다.
2. **첫 신호.** 병합한 KST 날짜보다 엄격히 뒤의 첫 주간 판단 세션이다. 등록 하한 **2026-10-30**보다 이르지 않다.
   - 2026-10-29 KST까지 병합하면: 첫 신호는 **2026-10-30(금)**이다. 2026-10-31(토) 실행이 기록하고, 일요일 실행이 예비다.
   - 2026-10-30 KST 이후에 병합하면: 첫 신호는 병합일 다음 주의 주간 판단 세션이다.
3. **병합 시점 제약.** 다른 작업의 미국 C1 정식 실행 승인과 execute 사이에는 main을 바꾸지 않아야 한다. 따라서 이 PR은 C1 execute가 끝난 뒤, 또는 승인 PR이 병합되기 전에 소유자가 직접 병합한다. 자동 병합하지 않는다.
4. **고정 대상.**
   - 이 연구의 두 파일은 바이트로 고정한다. 바뀌면 `CODE_CHANGED_SINCE_REGISTRATION`.
   - 직접 쓰는 연구 모듈 네 개도 바이트로 고정한다: `prospective_receipt_core`, `rp1_b_state_receipt`, `kr_bar_integrity`, `kr_selection_challenger`.
   - 봉인 FAST 함수, 임계값, KRX 달력 2026-10-01~2031-12-31은 동작으로 고정한다. 바뀌면 `SCIENTIFIC_DEPENDENCY_CHANGED`.
   - 정당한 변경도 새 연구 버전으로 한다.

## 4. 성과 평가 준비 — 차단 상태와 남은 결정

상태 관측과 성과 평가는 분리되어 있다.

- 상태는 신호일 영수증에 먼저 고정된다.
- 성과는 별도 기록이다. 만기 세션이 확정된 뒤에만 만들 수 있고(`prospective_receipt_core.has_matured`), 영수증을 고치지 않는다.
- 이 PR에서 `outcomes` 단계는 아무것도 내려받거나 계산하지 않는다. `BLOCKED_OUTCOME_CONTRACT_NOT_REGISTERED`만 기록한다.
- 명세의 `outcomeEvaluation`을 제자리에서 바꿔 계약을 등록하려 하면 거부한다.

**이미 고정된 것(원 문서 상속)**

- 통계량: 12-1 모멘텀 상위−하위 스프레드의 H63 값이 불리 상태에서 더 낮은가.
- 대상 신호: 기존 12-1 모멘텀이다. 새로 발견한 특징이 아니다.
- 상태별 비중첩 H63 블록이 6개 미만이면 `DESCRIPTIVE_ONLY_INSUFFICIENT_STATE_BLOCKS`, p=1이다.
- Holm α=0.05 가족은 (B-H1, B-H2)다. B-H2는 지지된 A 신호가 생기기 전까지 p=1이다.
- 미관측·미판정 상태는 어느 쪽에도 넣지 않는다.

**블록 기하**

`coverage.json`이 신호 시점 사실만으로 보고한다. 블록은 첫 적격 체결 세션부터 63세션 간격이다. 각 블록은 진입 직전 주간 판단 세션의 상태를 갖는다. 그 주에 영수증이 없으면 `unobserved`다. 이는 README B 진단의 관례를 물려받은 것이며, 성과 계약에서 확정해야 한다.
