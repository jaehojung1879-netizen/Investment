## 3. 검증기 결함 3건: 원인과 수리

### A. `collect-remaining` 호출 오류 — 해결

- **원인:** `kr22_repository_originals`가 `collect(plan, out, *callers)`로 위치 인자를 넘기는데, `collect`는 `list_page=`, `document=` 키워드 전용이다.
- **수리:** 키워드로 호출한다. 수집 후 목록 확인(§3.C)까지 끝내고 검증 결과를 출력한다. 기본 호출 상한은 400(문서 141 + 목록 141)이다.
- **새 명령 `confirm-remaining`:** 이미 받은 수집분에 목록 확인만 추가하고, 문서는 다시 받지 않는다.
- **회귀 테스트:** 실제 CLI 진입점을 가짜 OpenDART로 끝까지 돌린다. 옛 코드에서는 같은 `TypeError`를 재현하고, 새 코드에서는 141/141 검증으로 끝난다.

### B. 종결 정정 공시 검증 — 해결

**원인:** 실제 뷰어 제목은 `기관/서식명/날짜`이고 정정 표지가 없다(31/31). 그래서 기존 검증기가 제목에서 `[기재정정]`을 찾으면 31건 전부가 거부됐다.

**수리:** 정정 여부를 제목이 아니라 그 접수의 정정 신고 노드로 증명한다. 다음이 모두 맞아야 통과다.

1. `정정신고(보고)` 노드가 정확히 1개이고, 그 노드의 접수번호가 이 접수다.
2. 본문이 적은 신고일 = 접수일.
3. 본문이 적은 정정대상 = 이 보고서. 서식명만 적은 경우도 이 보고서로 인정한다(실제로 자주 그렇다). 단, 첨부서류명(평가의견서, 이사회 의사록)은 `[첨부정정]`에서만 인정한다.
4. 본문에 정정전/정정후 표가 있다.
5. 본문이 적은 최초제출일과 정확한 서식·세부유형으로, 고정 공시 색인에서 같은 발행사의 원본 공시가 **정확히 하나** 연결된다. 색인은 `signal-history` `d646a69`이며 blob 해시가 계획과 일치할 때만 읽는다.

제목은 여전히 검사한다. 서식명이 맞아야 하고, 제목 날짜가 접수일과 다르면 거부한다.

**반례 테스트:** 다음은 모두 거부된다.
- 정정 신고 노드가 없는 결정 공시
- 정정표 없는 "정정신고" 노드

### C. 배당결정 ZIP 검증 — 해결

**#294 진단 정정:** #294 보고서는 "cp949 때문에 발행사 검사가 깨진다"고 적었는데, 틀렸다.

- `zip_members`는 원래 UTF-8과 cp949를 모두 디코딩한다.
- 실제 원인은 141건 전부가 KRX 거래소 공시 서식(xforms HTML)이라는 점이다. 이 서식에는 DART XML 머리글(`COMPANY-NAME AREGCIK`)도, 법인코드·종목코드·접수번호도 본문에 없다.
- 그래서 발행사 검사가 141건 모두에서 실패했다. 22건은 추가로 ZIP 항목명 `/` 접두 때문에 그 전에 거부됐다.

**수리 1, ZIP 경로:** 앞의 `/` 하나는, 그 뒤가 경로 구성요소 하나일 때만 상대 이름으로 읽는다(`/<접수번호>.xml`). 나머지는 그대로 거부하고, 보호 규칙은 오히려 더했다.

- 계속 거부: 다른 절대경로(`/a/b.xml`, `//a.xml`), 역슬래시, 드라이브·스트림 콜론, 제어문자, 빈·`.`·`..` 구성요소.
- 새로 추가한 거부: 정규화 후 이름 중복, 심볼릭 링크, 암호화, 전체 크기 한도, 압축률 100배 초과(실제 141건은 4.5–7.7배), 선언 크기 불일치.
- 압축은 메모리에서만 읽고 디스크에 풀지 않는다.

**수리 2, 신원:** 머리글 없는 서식은 아래가 **모두** 맞을 때만 통과한다.

1. ZIP 항목이 하나이고, 이름이 `<접수번호>.xml`이다.
2. 머리글 날짜가 접수일과 같다.
3. 서식명이 배당 결정이다.
4. OpenDART `list.json`(법인코드 × 접수일)이 그 발행사가 그날 바로 그 접수번호로 배당결정을 냈다고 확인한다.

서식 머리글의 회사명(LIG손해보험, 현대증권, 아이엔지생명 등)은 공시 당시 이름이라 기록만 하고 신원 판정에는 쓰지 않는다. 사명 변경을 추정하지 않기 위해서다.

**반례 테스트:** 다음은 모두 거부된다.
- 목록 없음, 목록에 다른 접수 또는 다른 보고서
- 다른 법인·날짜의 목록 행
- 다른 접수명의 항목, 다른 머리글 날짜, 다른 서식, 항목 2개
- 악의적 ZIP 7종(심볼릭 링크, 중복, 압축 폭탄, 경로 순회, 항목 과다, 디코딩 불가, 암호화)과 전체 크기 초과

**실데이터 결과:**
- 목록 확인 전에는 141/141이 "발행사 미증명"으로 막힌다. 증거 없이는 승인하지 않는다.
- 목록 확인 후 141/141 검증.
- cp949 114건, `/` 접두 22건 모두 정상 처리됐다.

## 7. 보존과 재현

- **커밋하지 않은 것:** 원본 바이트. 재배포 권리가 확인되지 않았다.
- **커밋한 것:** 접수번호, 출처, 원본 SHA-256, 목록 확인 응답 SHA-256, 공개 시점(접수일), 배당 다운로드 시점, 검증 결과. 정정 행은 앞 160자만 담았다.
- **시각 기록 공백:** 종결 정정 수집기는 응답별 시각을 기록하지 않는다. #294 실행 시각(2026-10-26 약 14:33–14:36 UTC)만 남아 있다.
- **소실 위험:** 원본은 이 세션의 임시 디렉터리에만 있고, 컨테이너가 회수되면 사라진다.

재취득 절차는 키 값을 출력하지 않는다. 출력 디렉터리는 비어 있어야 한다.

```
python -m research.industry_alpha_next_v1.kr22_terminal_viewer collect --output <빈 디렉터리 A>      # 키 불필요, ≤560회
DART_API_KEY=… python -m research.industry_alpha_next_v1.kr22_repository_originals collect-remaining --output <빈 디렉터리 B>  # ≤400회
python -m research.industry_alpha_next_v1.kr22_real_data_verification --viewer A --dividends B --evidence <#294 evidence.json>
```

마지막 명령은 모든 원본을 #294의 SHA와 대조한다. 바뀐 원본은 `stage2Integrity: false`로 따로 드러나며, 덮어쓰거나 무시하지 않는다.
